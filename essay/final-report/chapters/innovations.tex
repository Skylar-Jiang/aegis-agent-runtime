\chapter{创新性说明}

\section{创新设计的出发点}

Agent 安全并不只是给模型增加一条“不要做危险事情”的提示。对于能够调用工具的系统，风险发生在真实资源被读取、修改、保存或发送的时刻；而一个任务通常由多个相互依赖的动作组成。若只在输入端做一次过滤，后续工具输出、Memory 和任务状态仍可能改变系统行为；若只在每个工具前加一条规则，又难以说明取消后哪些结果应被保留、哪些结果应被恢复。Aegis Runtime 的创新设计从这一现实问题出发，将执行过程、调度过程和恢复过程放在同一运行时框架下处理。

本作品的三项核心创新分别解决“副作用何时生效”“审批如何影响任务推进”“异常后恢复到什么范围”三个问题。它们之间具有递进关系：先让单个可恢复操作具有清晰生命周期，再让多个任务节点在审批状态下保持正确推进，最后在局部失败或取消时依据关联关系选择性恢复。Risk、Policy、Permission、Approval 与 Audit 为这三项机制提供判断、授权和可追溯支撑，但不替代三项核心创新本身。

\section{Transactional Controlled Execution}

第一项核心创新是 \textbf{Transactional Controlled Execution}。它把可恢复工具调用从“函数返回即完成”的模式，转变为“先受控、再提交”的生命周期。对于文件修改、Memory 写入和下载等会留下状态的操作，系统在适用时建立 Checkpoint，将候选结果登记为 \code{PENDING} Effect；只有通过必要检查后，结果才进入 \code{COMMITTED}。若审批被拒绝、任务被取消或检查失败，系统依据已登记的关联关系将其清理、拒绝或回滚。

这项创新的关键不在于使用了多少状态名称，而在于区分了“工具已经响应”和“资源已经安全生效”两个事实。前者可能只是某个执行器完成了调用，后者则要求目标、权限、任务关联和检查条件都满足。通过这一分离，系统可以避免把未经验证的候选结果直接作为可信成果，也可以在取消发生时处理仍处于待处理阶段的影响。

Transactional Controlled Execution 还使用户能够理解资源状态。前端以脱敏方式呈现 Effect 类型、资源引用、Checkpoint、当前状态以及回滚或保留原因；Audit 记录与之对应的状态变化。用户不需要阅读底层日志，也可以区分某项内容是“尚未提交”“已经提交”还是“已经恢复”。这种可见性服务于实际决策，而不是暴露敏感工具输出。

该机制的边界同样明确：本作品使用“事务式”描述工程级的受控提交与恢复，不宣称完整 ACID、分布式事务或服务重启恢复。它只对已被纳入 Effect、Checkpoint 和关联关系管理的可恢复状态提供处理依据；对不可逆外部动作，系统的重点是通过审批和提交边界在释放前控制风险，而不是声称事后可以通用撤销。

\section{Approval-aware TaskGraph Scheduling}

第二项核心创新是 \textbf{Approval-aware TaskGraph Scheduling}。传统的审批机制容易出现两种极端：要么只暂停一个按钮，却让相关任务仍在后台推进；要么为了安全而冻结整个任务，连与风险无关的独立工作也无法继续。Aegis Runtime 将审批状态与任务依赖、资源冲突共同纳入 TaskGraph 调度，使审批成为改变运行时行为的真实状态，而不是界面上的附加提示。

当高风险节点进入 \code{WAITING\_APPROVAL} 时，系统不会允许该节点直接执行；依赖这一节点的后续节点也不能越过等待状态；触碰同一 Effect target 的冲突节点同样受到约束。与此同时，无依赖且无冲突的独立节点可以继续推进。这样，系统既能保持审批边界，又不会把整个任务图无差别暂停。Grant 后，满足条件的节点恢复调度；Deny 后，目标及依赖路径被阻断；Cancel 后，受影响节点收敛并进入后续状态处理。

这项创新强调的是“审批与调度的一致性”。用户的决定不仅保存在审批列表里，还会同步影响图中的节点状态、后续 Effect 处理和 Audit 记录。全局 Approval 查询与按任务查询都保留 task 关联，便于用户从待办事项回到实际任务，而不会产生跨任务误操作。对于多步骤任务而言，这种关联让“我同意了什么、系统接下来会做什么”具有清晰的对应关系。

当前原型将同一节点内部的 speculative overlap 明确标为 \code{NOT\_SUPPORTED}，也不宣称具备分布式调度能力。这一限制不是功能缺失的掩盖，而是为了保证当前实现范围内的节点状态、审批边界和 Effect 关联能够被完整验证。

\section{Dependency-aware Selective Rollback}

第三项核心创新是 \textbf{Dependency-aware Selective Rollback}。它解决的不是“是否能够执行一次回滚”，而是“出现问题后究竟应该恢复哪些影响”。在多步骤任务中，部分 Effect 可能已经安全提交且与问题无关，另一些 Effect 则仍在待处理状态或处于受影响依赖闭包内。若按整个任务全部清空，会误删独立成果；若只停止任务而不处理受影响状态，又可能留下不一致资源。

系统通过 TaskGraph、Effect、request、Checkpoint 和资源目标之间的关联确定回滚范围。回滚计划在产生资源变化前进行 Preflight，检查对象是否存在、是否属于当前任务以及关联是否一致。跨任务引用、未知对象或关系不一致的请求会被整体拒绝，避免先处理一部分再发现范围错误。范围确认后，执行器只回滚受影响依赖闭包内的可恢复 Effect；范围外且已经安全提交的独立 Effect 被保留或标记为 \code{PRESERVED}，并说明保留原因。

这项创新同时保护用户已有工作。当系统发现提交后用户又修改了同一资源时，不会用旧 Checkpoint 覆盖用户的新内容；它会保留用户内容，并把残留状态和原因记录下来。对于重复提交的同一回滚计划，已处理 Effect 不会被再次修改，从而保持幂等性。对用户而言，这意味着取消和恢复不再是一个不可解释的“还原按钮”，而是能够看到处理范围、保护理由和最终状态的过程。

\section{三项创新的协同价值}

三项核心创新构成了一条从预防到恢复的闭环。Transactional Controlled Execution 解决单个副作用的可控性；Approval-aware TaskGraph Scheduling 解决多节点任务在等待、授权、拒绝和取消时的有序推进；Dependency-aware Selective Rollback 解决局部问题发生后如何避免扩大影响。没有受控 Effect 生命周期，回滚就缺少可靠的状态依据；没有审批感知调度，用户的授权决定可能与任务实际推进脱节；没有选择性回滚，取消就可能演化为对全部成果的粗暴清空。

Risk、Policy、Permission、Approval 和 Audit 贯穿其中。它们负责识别风险、表达规则、绑定用户决定并保留过程事实，但作品的创新落点是三项机制在同一 Runtime 内形成的可执行组合。正式实验和浏览器场景表明，安全判断、任务调度、Effect 状态与审计记录可以在当前受控环境中保持一致；同时，作品也不把这一结果外推为对开放网络、不可逆外部操作或分布式系统的通用保证。
