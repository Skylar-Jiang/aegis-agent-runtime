\chapter{作品设计与实现}

\section{总体设计思路}

传统的工具调用往往把一次操作看成简单的“发出请求—获得结果”：模型决定调用什么工具，工具执行后返回成功或失败。这样的方式在只读查询中较为直接，但当工具会修改文件、写入 Memory、下载内容或执行命令时，仅以一个返回值表示全部过程就不够了。用户真正关心的是：系统是否在正确的时机执行了操作；高风险步骤是否获得了确认；操作发生后留下了什么影响；如果任务被取消，哪些影响需要恢复。

为回答这些问题，Aegis Runtime 把 Agent 的一次行动拆成若干可检查的环节。Planner 负责提出下一步建议，Runtime 负责根据风险和任务状态决定是否允许该建议进入执行，执行器负责在受控边界内操作资源，Effect 记录负责保存这次操作与资源状态的关系，Audit 负责保留过程中的关键事实。各部分不是各自独立地工作，而是围绕同一个 task 标识和关联关系协作。用户在界面中看到的任务进度、审批卡片、Effect 状态和审计事件，正是这条链路在不同阶段的可见投影。

这种设计可以用日常的“办理事项”来理解。Planner 相当于提出办理建议；风险和权限机制相当于先检查事项是否合规；Approval 相当于在需要时请用户确认；受控执行相当于先把材料放进待办区、核对无误后再正式归档；Effect 和 Audit 则相当于为每一步留下可查的业务记录。系统并不是让每一项操作都变得复杂，而是在会产生真实影响的地方增加必要的确认点和恢复依据。

\section{系统组成与职责分工}

系统的第一层是任务与调度层。用户提交任务后，Runtime 将其组织为由节点和依赖关系构成的 TaskGraph。一个节点可以代表读取、写入、审批等待或其他受控动作；边表示“必须先完成什么”或“不能与什么同时影响同一资源”。图中的节点状态使系统能够区分尚未开始、等待审批、正在执行、已完成、被阻断和已取消等情况。这样的表示方式让系统不会因为一个高风险节点停下，就失去对整个任务的判断能力。

第二层是风险、策略和权限层。Risk 用于识别操作的风险信号，Policy 用于表达允许、阻断或需要审批的规则，Permission 用于核对请求是否在授权边界内。三者共同决定某项工具调用的处置方式。它们是运行时的支撑机制，而不是单独的“安全口号”：每次判断都会与具体请求关联，并在后续的审批、执行和审计中保留相应理由。对不满足条件的操作，系统采用 Fail-Closed 思路，即不把“无法确认是否安全”默认解释为可以继续执行。

第三层是 Effect 与 Checkpoint。Effect 可以理解为“已经准备或已经产生的资源影响”的记录，例如某个文件将被修改、某条 Memory 将被写入、某个下载对象将被接收。Checkpoint 则保存恢复所需的前置状态或关联信息。两者共同回答“这次操作影响了什么”和“如果需要恢复，应从哪里开始”。第四层是呈现与审计层：Task、Approval、Runtime、Effect、Audit 与 Dashboard 页面分别从不同视角展示同一条执行链路，页面只展示脱敏后的资源标识、状态和原因，不展示密钥、原始不可信输出或隐藏推理。

\section{从任务提交到完成的受控流程}

用户发起任务后，系统首先为任务分配统一标识，并依据任务内容构建可执行节点。节点在进入工具调用前，需要通过风险、策略与权限检查。对于普通且符合授权边界的动作，系统可以继续推进；对于需要用户确认的动作，节点转入 \code{WAITING\_APPROVAL}。此时界面会呈现与具体任务关联的审批信息，用户看到的是将要执行的受控动作及其风险原因，而不是由模型自由生成的笼统说明。

当用户选择 Grant 时，系统会把同意结果写回对应任务和节点，满足条件的节点继续进入执行。当用户选择 Deny 时，目标节点以及依赖于该节点的后续路径被阻断，不再跨越审批边界执行。若用户选择 Cancel，系统停止受影响的执行路径，并进入后续的范围判断与状态恢复流程。这样，Grant、Deny 和 Cancel 不是界面上的三个孤立按钮，而是会改变 TaskGraph、Effect 和 Audit 中关联状态的运行时事件。

在任何阶段，系统都不会把所有节点一概并行。对于同一资源目标可能产生冲突的操作，调度器会根据任务依赖和资源关联约束顺序；对于无依赖且无资源冲突的节点，则允许在安全条件满足时独立推进。当前原型明确不支持同一节点内部的 speculative overlap（\code{NOT\_SUPPORTED}），也不把本地单进程调度描述为分布式协调。这一边界使系统的行为保持可理解和可验证。

\section{Transactional Controlled Execution：让副作用先可控、后生效}

对文件、Memory 和下载等可恢复副作用，Aegis Runtime 采用 Transactional Controlled Execution。这里的“事务式”并不等同于数据库完整 ACID 事务，也不表示系统能够撤销所有外部世界行为；它表达的是一种工程上的受控提交与恢复过程。系统在适用时先保存必要的 Checkpoint，把候选结果登记为待处理的 Effect，再依据检查结果决定提交、拒绝、清理或回滚。

以文件修改为例，系统不会把候选内容一生成就直接视为可信成果。它先确认操作目标是否位于允许的工作范围内，检查路径和任务关联是否一致，并为可恢复的修改保存相应的前置状态。候选结果处于待处理阶段时，Effect 状态为 \code{PENDING}；只有必要条件满足后，文件修改才成为 \code{COMMITTED}。如果检查不通过、审批被拒绝或任务取消，系统不会把这次待处理操作伪装成已经完成，而是依据实际处理结果记录为 \code{REJECTED}、\code{CLEANED} 或 \code{ROLLED\_BACK}。

这种做法的作用在于把“工具已经返回”与“资源已经安全生效”区分开来。工具调用可能成功返回，但它仍可能对应错误路径、不符合权限要求的目标，或与任务状态不一致的请求；只有通过提交门后，系统才把结果作为可信状态。相反，任务在提交前被取消时，系统可以根据已有记录清理待处理内容，而不是等待错误状态进入后续环节后再补救。

\section{文件、Memory 与下载的状态管理}

文件是最直观的副作用类型。对于可修改文件，系统首先检查目标是否落在允许范围内，再建立与请求关联的 Checkpoint。提交后，Effect 记录保留资源目标、检查点和状态摘要；当需要回滚时，执行器再次核对任务、请求、Effect 和 Checkpoint 的关系，避免把一个任务的恢复操作作用到另一个任务。若系统提交后用户又手动修改了同一文件，当前内容已经不再等于系统提交时的内容，运行时会优先保护用户后写入的内容，并把无法安全覆盖的情况记录为可解释的残留，而不是用旧状态悄悄覆盖新内容。

Memory 的难点在于它会影响之后的任务。若未经检查的内容立即进入长期 Memory，后续 Planner 可能把它当成可信前提，从而放大一次错误输入。Aegis Runtime 因此把新写入内容置于受控状态，只有完成必要校验和提交后才进入可用范围。当某个新版本需要撤销时，系统处理的是该 Key 对应的受影响版本，并重新暴露此前可信的版本；其他 Key 和独立版本不应因为一次局部错误而被清空。这样，Memory 不再只是“是否写入成功”的二元结果，而具有“是否已验证、当前哪个版本可信、发生问题后应恢复到哪里”的状态含义。

下载同样需要先隔离后使用。下载对象可能来自外部地址，因而需要与来源、隔离对象和 Effect 记录建立关联。在进入可信工作区之前，系统可以对协议、地址和响应边界进行控制，并保持其可追溯性。若下载被拒绝或纳入回滚范围，系统只处理对应对象；与其无关、已安全提交的隔离对象不会被一并删除。对于用户而言，这意味着一个任务中发生问题的下载不会自动否定其他独立、已确认的成果。

\section{风险判断与用户授权如何衔接}

风险判断的价值不在于给任务贴上一个抽象的“高风险”标签，而在于帮助系统决定下一步应该怎样做。Aegis Runtime 在操作真正发生前，结合工具类别、资源目标、请求参数及其与当前任务的关系，判断该动作是否可以在现有授权范围内继续。例如，只读处理已授权资料与覆盖既有文件、向外部地址发送内容，所需要的确认程度并不相同。系统把这种差异转换为可执行的处置：在条件明确满足时放行；在需要用户决定时转入审批；在违反策略或权限边界时阻断。对于无法可靠确认安全性的情况，系统不会以“先执行再说”的方式扩大影响。

这一过程并不要求用户逐条审阅内部规则。需要审批时，页面以与任务关联的审批卡片呈现即将发生的动作、经过脱敏的目标信息和触发原因，帮助用户在有限信息中作出明确决定。用户授予许可后，系统仅让该任务中满足前置条件的节点继续；用户拒绝后，系统只阻断目标节点及其依赖路径。风险、Policy 和 Permission 因而是支撑用户授权的机制：它们负责把复杂的条件判断收束为“可以继续、需要确认、不能继续”这类可理解的选择，而不是替代用户作出超出授权边界的决定。

为了让授权结果可以追查，风险判断、规则命中、审批创建、用户决定和后续执行都会形成关联事件。用户不必查看原始工具输出，也能从 Audit 中看到某个节点为何等待、由谁决定以及决定后发生了什么。这样做既避免把安全提示做成难以理解的技术术语，也避免将敏感输入或隐藏推理暴露到前端。作品所追求的是全过程审计可追溯性：重要状态变化有依据、有时间顺序，也能与具体任务和资源影响对应起来。

\section{状态一致性与异常处理原则}

一个受控任务往往同时涉及节点、审批、Effect、Checkpoint 和审计事件。若这些记录彼此脱节，用户可能看到“任务已结束”，而某个待处理副作用仍悬在系统中；也可能已经取消任务，却又被误恢复执行。为避免这类理解和操作上的矛盾，Aegis Runtime 用统一任务关联把这些状态连接起来：审批决定只作用于对应任务，Effect 与产生它的请求和 Checkpoint 对应，图状态变化会写入审计事件，页面从同一组结构化状态中读取展示内容。

异常发生时，系统优先按照副作用所处阶段处理，而不是用一条笼统的失败提示掩盖差异。尚未产生资源影响的节点可以被阻断；处于待处理状态的 Effect 可以清理或回滚；已经安全提交但未被影响范围覆盖的独立 Effect 应被保留。取消任务后，运行时会使相关后台处理收敛，并拒绝再次恢复已经终止的任务，以免同一任务重复产生副作用。对于存在资源冲突的操作，调度器维持必要顺序；对于无依赖、无冲突的操作，才允许其独立推进。

这里的“一致性”是面向当前运行过程的工程约束，而不是对完整 ACID、跨服务分布式事务或服务重启恢复能力的宣称。它强调的是：在本原型覆盖的状态和资源类型内，同一项决定应当在图、Effect、审批和审计中得到相互吻合的呈现；当系统无法安全继续时，应当停止在可解释的状态，而不是悄悄留下不明来源的结果。这也是后续测试以状态变化、影响范围和审计链路为重点的原因。

\section{审批感知的 TaskGraph 调度}

审批的目的不是让用户在每一步都点击确认，而是在操作可能突破授权边界或造成较大影响时，把决定权交还给用户。Aegis Runtime 为 Approval 提供全局查询和按任务查询两种视角：用户既能查看当前所有待处理审批，也能回到某个任务中查看与该任务关联的审批记录。审批响应中保留 task 标识，使前端能够准确回到对应 Runtime 页面，而不会把一个任务的决定误用于其他任务。

在一个有多个节点的任务中，如果某个高风险节点等待审批，最简单的做法是暂停整个任务。这种方式看似保守，实际上会把与风险无关的安全工作也一并停下。Aegis Runtime 采用 Approval-aware TaskGraph Scheduling：等待审批的节点不会被执行；依赖它的后续节点也不能越过这一边界；与其争用同一资源目标的节点同样受到约束。与此同时，不依赖该节点、也不触碰冲突资源的独立节点仍可继续推进。这样既避免审批被绕过，又减少不必要的停顿。

Grant、Deny 和 Cancel 分别对应不同的图状态变化。Grant 表示用户同意在既定范围内继续，满足条件的节点恢复调度；Deny 表示目标动作不应执行，依赖路径随之阻断；Cancel 表示任务进入终止处理，后台执行需要收敛，已经处于待处理或受影响范围内的 Effect 进入回滚判断。任务达到取消终态后，Resume 会被拒绝，防止已经结束的任务再次启动并产生重复副作用。这些状态变化既在图中可见，也会在 Audit 中留下事件记录。

\section{Dependency-aware Selective Rollback：只恢复应恢复的部分}

现实任务中，失败和取消往往只影响其中一部分。例如，任务可能已经安全保存了一份独立文件，同时另一项 Memory 写入仍处于待处理状态；此时若用户取消任务，合理做法不是把所有已完成成果都删除，而是恢复真正受影响的部分，并保留已经安全提交、与问题无关的成果。Dependency-aware Selective Rollback 正是围绕这一问题设计。

系统通过 Effect、request、Checkpoint、task 和资源目标之间的关联确定范围。回滚计划在执行前先完成 Preflight：核对目标是否存在、是否属于当前任务、关联关系是否一致。若计划混入了跨任务对象、未知对象或不一致的引用，系统会在真正修改资源之前拒绝整项计划。这样可以避免“先恢复一部分，后来才发现范围越界”的问题，也使拒绝行为本身保持零额外副作用。

确定范围后，执行器只处理受影响依赖闭包中的 Effect。已安全提交且未进入该范围的独立 Effect 不会被加入回滚队列，而是保持或标记为 \code{PRESERVED}，并在界面和 Audit 中说明保留原因。对于同一资源目标存在多个关联 Effect 的情况，系统按既定的关联顺序恢复；对于计划外资源，则不作额外动作。重复执行同一已完成回滚计划也不会重复修改资源，从而避免重试导致的状态漂移。

\section{面向用户的脱敏展示与审计闭环}

作品的前端不把运行时内部细节直接暴露给用户，而是采用脱敏投影展示与决策有关的信息。Runtime 页面可以从任务直接跳转并携带对应 task 标识，集中展示节点状态、Effect 类型、资源引用、Checkpoint 标识、提交或回滚状态及原因。Approval 页面用于查看和处理待确认事项；Graph 页面展示依赖与收敛状态；Effect 页面展示资源影响；Audit 页面按时间串联风险判断、审批、执行、提交、回滚和保留事件；Dashboard 汇总三组正式实验的核心指标。

这种展示方式有两个目的。第一，用户无需阅读日志或源代码，也能理解当前任务为何等待、何时恢复、哪些资源受到影响。第二，安全敏感信息不会因“提高透明度”而被再次泄露：页面不展示密钥、原始不可信内容、完整工具输出或隐藏推理，只展示完成判断所需的状态、关联标识和理由。由此，系统把可追溯性建立在结构化事实之上，而不是建立在暴露敏感内容之上。

\section{典型任务过程说明}

以“整理资料并生成一份可提交文件”的任务为例，系统可以先读取允许范围内的资料并处理不涉及外部影响的节点；当任务准备覆盖某个已有文件或执行高风险操作时，该节点进入等待审批状态。用户同意后，系统在保存前建立 Checkpoint，将候选结果作为待处理 Effect 登记，检查通过后再正式提交。若用户在提交前取消任务，待处理 Effect 会进入回滚处理；若任务中另有一份独立文件已经安全提交且不在受影响范围内，该文件会被保留并说明原因。

这一过程把抽象的安全规则转化为用户可以观察的行为：应当等待的操作确实等待，应当继续的独立工作可以继续，应当恢复的状态被恢复，不应受到影响的独立成果不被误删。作品的实现重点正是让这些状态在 Runtime、Approval、Graph、Effect 和 Audit 中保持一致，而不是只在某个单独页面上显示一条“操作成功”或“操作失败”的提示。
